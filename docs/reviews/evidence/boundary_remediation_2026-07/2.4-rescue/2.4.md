### A2. THE FRAME-NESTING TABLE (the brief's "correct level" question)

**Trigger is substitution-origin ONLY.** A plain syntax error in the identical
position is non-fatal in BOTH shells (`eval 'if'; echo AFTER` → rc 0, AFTER
runs, both shells, all channels — `B3`, `a2`). This is exactly the typed fact
`SubstitutionSyntaxError` already carries.

**Scope of the abort = the shell PROCESS, as if by `exit`.** Not a frame-local
unwind. Evidence:

| case | frame | bash result | contained? |
|---|---|---|---|
| `E1` | function | rc 127/1, whole shell dies | **NO** |
| `E5` | `if eval ...; then` | rc 127/1, whole shell dies | **NO** |
| `E6` | `eval ... && echo AND` | rc 127/1, whole shell dies | **NO** |
| `D1` | source → eval | rc 127/1, nothing after at ANY level | **NO** |
| `D2` | eval → source | rc 127/1 | **NO** |
| `D3` | source → source | rc 127/1 | **NO** |
| `D4` | eval → eval | rc 127/1 | **NO** |
| `E2` | subshell `( )` | subshell dies rc 1, **parent continues rc 0** | **YES** |
| `E3` | cmdsub `$( )` | child dies, `$?`=1, parent continues | **YES** |
| `q4` | backtick | child dies, `$?`=1 | **YES** |
| `E4` | pipeline member | member dies, pipeline rc = last member | **YES** |
| `g3` | background `&` | child dies, `wait` rc 0, parent continues | **YES** |

i.e. **fork boundaries contain it; non-fork frames do not.** psh gets this
for free if the outcome is a `BaseException` that the existing child
boundaries already catch.

**EXIT traps run** — it is a real shell exit, not an abort (`q6`, `e3`):
bash `-c` prints `TRAPPED rc=127`; bash file prints `TRAPPED rc=257`.
(`q7` control: an explicit `exit 1` prints `TRAPPED rc=1` in both shells.)

**ERR traps do NOT run** (`h1`): bash with `set -E` + `trap ... ERR` aborts
without firing ERR; psh at base fires ERRTRAP and continues.

**Not strippable by `command`/`builtin`** (`a1`,`a3`,`a4`): `command eval`,
`builtin eval`, `command source` ALL still abort in bash (rc 127/1), while
the plain-syntax-error control under `command eval` is non-fatal in both.
→ the outcome must **NOT** be modelled as `SpecialBuiltinUsageError`
(which `command` strips by design).

**Interactive is fully exempt** (`interactive.py`, pty-driven): bash reports
the diagnostic and continues for direct-cmdsub, eval, source and procsub —
and a sourced file even continues to its OWN next line (`IN-AFTER` prints,
where non-interactively it never runs). psh at base also survives. **Both
shells survive today; the fix must keep it that way.**

### A3. THE STATUS RULE (the brief compresses this to "127"; it is richer)

Pre-error `$?` does **not** leak into the status (`q2`: `false;` / `true;` /
`(exit 9);` prefixes all give byte-identical results).

| discovery context | EXIT trap sees `$?` | process exit status |
|---|---|---|
| `-c` shell — anywhere in the `-c` string's execution (direct, or nested eval/source/function/trap, any depth) | 127 | **127** |
| file/stdin — error at that source's own top-level READER parse (direct) | 2 | **2** ← psh already correct |
| file/stdin — error inside an `eval`/`source` STRING | 257 (`EX_BADSYNTAX`) | **1** (257 & 0xff) |
| file/stdin — error in a TRAP ACTION string's own parse | — | **2** (not 1 — see O3) |
| forked child (subshell/cmdsub/pipeline/bg), ANY channel incl. `-c` | 257 (subshell) / 1 (cmdsub) | **1**; parent unaffected |
| any channel with **`set -e`** active | 2 | **2** (not 127/1 — see O2) |
| interactive | — | no abort at all |

The in-trap 257 is bash's internal `EX_BADSYNTAX` (= `EX_SHERRBASE`+1) leaking
through `$?` before the 8-bit truncation that produces the observable 1.

**The pins I own already encode BOTH statuses**, which corroborates the table:
`test_divergence_c_mode_exit_code_is_127_in_bash` asserts bash 127 in `-c`;
`test_divergence_eval_source_procsub_joined_i3` asserts bash rc **1** in FILE
mode. So "127" is the `-c` headline, not the whole rule.

## PHASE A — proposed design (awaiting GO)

Producer already exists (2.3): `SubstitutionSyntaxError` +
`is_substitution_origin()` in
`psh/parser/recursive_descent/helpers.py`. Missing piece is the **consumer**.

1. **One typed outcome**, `SubstitutionSyntaxAbort(BaseException)`, homed next
   to `TopLevelAbort` in `psh/core/exceptions.py`, carrying only the discovery
   context (`nested`: inside an eval/source/trap string vs the source's own
   reader parse). `BaseException` (like `TopLevelAbort`/`SystemExit`) so it
   unwinds past `except Exception` guards without tripping the internal-defect
   guard or the live Q2 broad-catch ratchets.
2. **One raise site**: the existing `except ParseError` clause in
   `SourceProcessor._execute_buffered_command` (+ the accumulator trial-parse
   error path in `execute_from_source`) — the single chokepoint where every
   channel's parse error already lands — gated on `is_substitution_origin(e)`
   AND non-interactive (`state.is_script_mode`, the predicate
   `_posix_syntax_abort` already uses; the immediate input source is NOT a
   reliable interactivity signal because an eval's StringInput is
   non-interactive even in an interactive shell).
3. **Propagation is free**: nothing catches `BaseException` on the
   eval/source/function/`if`/`&&`/trap paths, so the "not contained by
   non-fork frames" semantics falls out without touching those frames.
4. **Consumed at exactly two kinds of boundary**, both of which already exist
   and already handle `SystemExit`/`TopLevelAbort`:
   - **top level** — `SourceProcessor` (the `except SystemExit` site at
     `source_processor.py:95`, which sets the status and then calls
     `trap_manager.execute_exit_trap()`): gives bash's "EXIT trap runs and
     sees the abort status" for free;
   - **process/child boundaries** — `executor/child_policy.py`,
     `executor/strategies.py` (subshell/cmdsub/procsub/pipeline children):
     child exits **1**, parent untouched.
5. **One status policy function**, beside the other exit-status policy in
   `psh/core/internal_errors.py` — not scattered rc comparisons:
   errexit → 2; `-c` channel → 127; else nested → 1, reader-parse → 2;
   forked child → fixed 1.

**Design corroboration (read-only survey done while awaiting GO).** All THREE
fork paths — `child_policy.py:261` (inside `run_background_shell_child`),
`child_policy.py:353` (inside `run_child_body`; `run_child_shell` DELEGATES to
it rather than catching itself) and
`process_launcher.py:356` (pipeline members, background jobs, external
children) — already funnel through the SAME tuple
`child_policy.CHILD_EXIT_EXCEPTIONS` and the SAME
`child_policy.map_child_exception()` ("the ONE taxonomy every fork site
shares"). So the entire fork-containment half of the bash model is one tuple
entry plus one taxonomy arm (`SubstitutionSyntaxAbort → 1`), in one file — no
per-frame edits, no scattered rc comparisons. Symmetrically, the top-level
half is one clause beside the existing `except SystemExit` at
`source_processor.py:95`, which already calls `execute_exit_trap()`
afterwards and therefore reproduces bash's "EXIT trap runs and observes the
abort status" for free. The existing `TopLevelAbort` is deliberately NOT
reused: it is a *discard-and-resume* outcome contained at every buffered
boundary, which is the opposite of the process-scoped semantics measured in
A2.

## R7-A — MECHANISM PROPOSAL (written BEFORE the diff, per the streamlined
## stage-gate; the landing declaration carries it)

**The rule is already ours; round 6 applied it at one route out of three.**
Bash's severing rule — an ignored `set -e` reaches through a COMPOUND body or
a DIRECTLY-INVOKED function body and nothing else — was implemented for
pipeline members. The verifiers found the two other places it governs.

**(1) The BACKGROUND route.** A backgrounded BARE SIMPLE command must sever.
Proposed placement: `child_policy.py#run_background_shell_child` — the ONE
runner every in-process backgrounded child uses — gains a keyword
`sever_errexit_context`, and exactly one caller passes it: the backgrounded
BUILTIN strategy (`strategies.py#BuiltinExecutionStrategy._execute_builtin_in_background`),
which is the bare-simple route. The backgrounded FUNCTION and
subshell/brace/list routes deliberately do not pass it, because each
introduces a body. No deferral is parked here: the routes that would re-apply
it are exactly the ones that never sever, so the one-shot machinery is not
needed at this site.

**(2) The deferral must be ONE-SHOT, bound to the member's OWN resolved
command.** Round 6 re-applied it at ANY function-body entry inside the member,
so a function reached through the member's `eval`/`.` TEXT got it back.
Proposed placement: `command.py#_dispatch_resolved`, which is where a simple
command's resolution is already known — `resolved.dispatch_kind` is
`DispatchKind.FUNCTION` exactly when the member's own command IS a function.
A FUNCTION dispatch leaves the parked depth for `_function_frame`; **every
other dispatch discards it there**. That single line is what makes it
one-shot: the deferral cannot survive into anything the member merely starts.

**(3) The dropped seed (R7-C, same family).**
`executor/core.py#_execute_background_list` — the route for `a && b &` and
`for … done &` — was left on the pre-widening two-argument call and silently
took seed 0. It is a COMPOUND, so it must CARRY the depth; threading it moves
those rows to bash.

**Why this cannot leak:** (1) mutates a context only inside a forked
background child, from one caller; (2) clears a field that only a pipeline
member's closure ever sets, and clearing an unset field is a no-op for every
other command in the tree; (3) passes a value the sibling callers already pass.

**Domain stated, because the ruling asked what bash does at the OTHER routes:**
command substitution, backticks and process substitution do NOT sever — bash
carries the suppression into them and psh already matched (`r7a.py` rows
c1–c6, MATCH at base and at this tip, including their ordinary-errexit twins).
A substitution child is not a "bare simple command" in bash's sense; it is a
substitution, and its status rule is the child rule. No change was made there.
